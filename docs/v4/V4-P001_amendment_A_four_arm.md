## 1. The four arms

The frozen arm names are unchanged for A, B and C, because they are already embedded in frozen
hashes, artifact keys and the preregistration text. `C_VERIFIER_REPAIR` is the **correct verifier
diagnostic** arm; the owner's "C — CORRECT_VERIFIER_DIAGNOSTIC" and this name denote the same arm.
Arm D is added.

| Arm | Name | Message list after the frozen theorem prompt |
|---|---|---|
| A | `A_FRESH_RETRY` | *nothing*. The theorem prompt alone. No failed proof, no diagnostic, no mention that a previous attempt exists. |
| B | `B_SELF_REVISION` | `assistant`: the extracted failed proof. `user`: the frozen correction request. |
| C | `C_VERIFIER_REPAIR` | byte-identical to B, except the correction turn is the frozen request **plus** the theorem's own normalized, budget-bounded Lean diagnostic. |
| D | `D_MISMATCHED_DIAGNOSTIC` | byte-identical to C, except the appended diagnostic is the derangement-assigned **donor** diagnostic of a different theorem. |

Renderer: `src/tinylean_rl/evaluation/v4_prompts.py`, `RENDERER_VERSION = "v4-prompt-1"`. The
correction request is frozen once and shared, so the wording of B, C and D cannot drift apart:

> The previous proof attempt was rejected. Revise it into a correct and complete Lean proof of the
> same theorem.

The exact construction is enforced, not documented-by-convention. The renderer refuses to build an
arm that violates its own contract (`Arm A takes neither a failed proof nor a diagnostic`, `Arm B
must not carry a diagnostic`, `Arm D requires a normalized Lean diagnostic`), and
`diagnostic_arm_invariants()` returns the five machine-checked equalities:

```
c_is_b_plus_own_diagnostic                 c_tail == b_tail + "\n\n" + own
d_is_b_plus_donor_diagnostic               d_tail == b_tail + "\n\n" + donor
d_equals_c_with_own_replaced_by_donor      d_tail == c_tail[:-len(own)] + donor
c_and_d_share_prefix_before_diagnostic     c_tail[:-len(own)] == d_tail[:-len(donor)]
histories_identical_except_the_diagnostic  c[:-1] == d[:-1] == b[:-1]
```

All five hold on the audited example (`V4-P001_prompt_audit.json → frozen_example.arm_d_invariants`),
and the D-arm rendering was verified to equal the C-arm rendering with the own diagnostic text
replaced by the donor text on **every one of the 1371 pool theorems**
(`prompt_lengths.arm_d_rendering_is_c_with_the_donor_diagnostic_on_every_theorem = true`).

### 1.1 What Arm D is for

Arm D is a **mechanism / falsification** arm. It does not replace the frozen C−A and C−B primary
questions and it does not enter the GO gate (§7). Its only job is to separate two readings of a
positive C−B result:

* the model used something **specific to this theorem's failure**; or
* the model merely responded to *the presence of Lean-error-like text* in the correction turn.

If C beats D, supplying the *right* diagnostic is better than supplying *a* real diagnostic of the
same syntax. If C does not beat D, the honest claim is the weaker one — see §6.3 for the exact
wording rule this binds the paper to.

## 2. The diagnostic derangement (owner §2)

Producer: `src/tinylean_rl/evaluation/v4_derange.py` (`DERANGEMENT_VERSION = "v4-derange-1"`).

The mapping cannot exist before the primary cohort's diagnostics do, so only the **algorithm** is
frozen here. The rollout runner applies it inside the Stage-1/Stage-2 freeze boundary and stores the
mapping and its hash **before any second-stage generation** (§9, and §12 of the owner directive).

Frozen rule:

1. **Group** the 128 primary first-attempt failures by their frozen error category
   (`v4-taxonomy-1`). Category order is the frozen order, not an observed frequency order.
2. **Within a category of size ≥ 2**, order members by `(token-length bucket, sha256(statement_id))`
   and **shift the diagnostics cyclically by one position**. Every member is a donor exactly once
   and no member can receive its own diagnostic.
3. **Singleton categories** take the deterministic fallback, in recipient `(bucket, hash)` order:
   among theorems that are neither the recipient nor an already-used fallback donor, take the one
   minimising `(|bucket difference|, sha256(statement_id))`. The recipient always receives exactly
   one donor; donor reuse is possible *only* through the fallback and is reported.

Token-length buckets (`BUCKET_EDGES = (64, 128, 256)`) are the owner's optional refinement: they
match the diagnostic *size* of donor and recipient inside a category, so the Arm-C and Arm-D turns
differ in content rather than in length wherever the rule can arrange it. The normalizer caps every
diagnostic at 512 tokens, so bucket 3 is the top.

The rule reads only frozen statement ids, frozen first-attempt error categories and normalized
diagnostic token counts. It reads no model outcome, no verifier result and no second-stage label —
`_validate()` rejects a cohort with duplicates or an unknown category, and `derange()` raises rather
than returning a mapping whose invariants fail (`no_self_diagnostic`, `every_recipient_assigned_exactly_once`,
`all_recipients_distinct`).

The artifact reports exactly what the owner asked for: `same_error_category_match_rate`,
`diagnostic_token_length_difference` percentiles, `fallback_count` + `fallback_recipients`,
`donor_reuse_count`, the full `mapping`, and `mapping_sha256`.

## 3. Differential censoring (owner §5)

Per arm, `r_arm = unresolved infrastructure-censored candidates / 128`. `censoring_range =
max(r) - min(r)` over the four arms (`v4_stats.censoring_range`, which validates that every rate
lies in [0, 1]).

* **Primary analysis** uses complete valid A/B/C/D quadruplets only.
* If `censoring_range > 0.05`, the scientific classification is
  `D_INCONCLUSIVE_BY_DIFFERENTIAL_CENSORING`, regardless of the effect sizes. The GO taxonomy is
  not evaluated.
* **Sensitivity, reported separately and never redefining the primary endpoint**: all
  infrastructure-censored arm outcomes are read as failures, for C−A, C−B and C−D
  (`paired_gate_infra_as_failure`). The function also returns the number of pairs the reading had to
  complete with a censored arm — a data-completeness diagnostic, not a scientific quantity.

An infrastructure-censored arm stays **missing**, never a proof failure, in the primary analysis.
This is the §16 requirement that the runner must never convert infra into proof failure, carried
into the analyzer.

## 4. Data guard and guard order (owner §6)

Nominal cohort `N = 128`; the primary analyzable unit is a valid A/B/C/D quadruplet; the minimum
stays `N_complete >= 103` (`v4_stats.DATA_GUARD_MIN`, unchanged from the preregistration, and
explicitly not lowered after seeing anything).

The guards are evaluated in the frozen order, and the analyzer implements that order mechanically:

```
provenance
  -> N_complete guard            < 103          => D_INCONCLUSIVE_BY_DATA
  -> differential-censoring guard  range > 0.05 => D_INCONCLUSIVE_BY_DIFFERENTIAL_CENSORING
  -> primary paired gates        C-A, C-B
  -> specificity analysis        C-D            (mechanism label only)
  -> mechanism / descriptive     B-A, transitions
```

No scientific GO is reachable while either guard fails: `decide_outcome()` returns a `D_*` outcome
before it looks at a single gate. This is checked in the fixtures (§11).

## 5. Balanced arm execution order (owner §7)

Producer: `src/tinylean_rl/evaluation/v4_schedule.py`, artifact
`experiments/manifests/v4/v4_p001_arm_schedule.json`.

There is no fixed A→B→C→D per theorem. The schedule is a pure function of the formal theorem rank
(1..128) — no source, error category, diagnostic or outcome enters it — and it is frozen here, in
the same pre-outcome state as the seeds, so that the execution order of the four candidates of a
theorem cannot be chosen after any second-stage outcome exists.

Construction: five full cycles of all 24 permutations of the four arms (120 rows) plus 8 rows formed
from rotations of two edge-disjoint directed 4-cycles, `(0,1,2,3)` and `(0,3,2,1)`. The result is
exactly balanced:

* each arm appears **32 times in each of the four positions** (4 arms × 4 positions × 32 = 512
  candidates);
* every ordered predecessor pair `X -> Y` occurs **30–33 times** (12 pairs, uniform within
  rounding).

```
arm_schedule_hash = 9e090325ac19cf54cb5a7d68507fb97d632a49802e15c2b5dc21ce4ae617da73
```

The hash is cross-checked against a canonical-JSON re-serialization of the schedule rows inside the
artifact (`schedule_canonical_sha256_cross_check`), so it is reproducible by a third party without
running the producer's key order.

## 6. Statistics, classification and mechanism labels (owner §3, §13, §14)

### 6.1 Primary statistics, unchanged

Paired at the theorem level, one success definition per arm (canonical score == 1 under the same
format-gated Lean verification):

* `Delta_repair = mean(C_i - A_i)`, `Delta_diagnostic = mean(C_i - B_i)`;
* one-sided **exact** paired McNemar on the discordant pairs (`mcnemar_exact_greater`, integer
  arithmetic, no scipy);
* paired theorem percentile bootstrap 95 % CI (10 000 reps, frozen seed 20260925);
* raw paired effect reported in percentage points.

`B - A` is descriptive only. **AUPRC and any predictive metric are explicitly not endpoints here.**

### 6.2 Classification (unchanged vocabulary)

`A_VERIFIER_SPECIFIC_GO` requires C−A **and** C−B to pass; `B_SELF_REVISION_ONLY` requires C−A to
pass; otherwise `C_NO_REPAIR_GAIN`; plus the two `D_INCONCLUSIVE_*` outcomes of §3–§4.

### 6.3 Specificity and the mechanism label (new)

`Delta_specificity = mean(C_i - D_i)` is reported with the same statistics — raw paired effect,
exact one-sided McNemar, paired bootstrap 95 % CI — under a **directional rule with no effect-size
threshold**:

```
DIAGNOSTIC_SPECIFIC     Delta_specificity > 0  and  McNemar p <= 0.05  and  bootstrap CI lower > 0
DIAGNOSTIC_NONSPECIFIC  otherwise
NOT_EVALUABLE           a guard ended the study
```

No arbitrary large threshold is attached to C−D. What makes the rule interpretable instead is the
power analysis (§7): it says what C−D effect the rule can actually see at N = 128, and it measures
how often the rule fires when the true C−D effect is exactly zero.

**The mechanism label is appended to, never merged with, the classification.** `A_VERIFIER_SPECIFIC_GO`
continues to mean C vs A **and** C vs B, with no C−D requirement. `mechanism_label()` returns
`NOT_EVALUABLE` whenever a guard ended the study, so a `D_*` classification can never carry a
mechanism claim.

**Wording rule binding the paper.** If the C−D evidence does not support a positive theorem-specific
effect, no text may claim that the model understood the theorem-specific Lean diagnostic. The
permitted claim is the weaker one:

> supplying verifier diagnostic text improved repair relative to no diagnostic

and never anything stronger.

## 7. Power re-run with four arms (owner §4)

Producer: `scripts/v4_p001_power.py`; artifact `experiments/manifests/v4/v4_p001_power.json`. This
is a **design check under stated hypothetical probabilities**, not a prediction of any V4 outcome,
and it reads no V4 outcome (there are none).

### 7.1 Correction carried into this run

The previous three-arm artifact applied the C−A conjunction — including `Delta >= 0.08` — to both of
its keys, so its C−B rows **understated** C−B gate power. Each comparison now reports the power of
its own rule. The C−A and C−B thresholds themselves are unchanged; only the reported numbers are
corrected, and the correction is recorded in the artifact (`correction_vs_previous_run`).

### 7.2 The McNemar component, computed exactly

Under a baseline success probability `p_arm` and a compared-arm probability `p_other`, the discordant
counts are independent binomials, `K_favor ~ Bin(n, p_other(1-p_arm))` and
`K_against ~ Bin(n, p_arm(1-p_other))`. The exact one-sided rule's power therefore depends only on
`(q_total, delta)`, where `q_total = q_favor + q_against` and `delta = p_other - p_arm`, with the
feasible range `0 <= delta <= q_total`. This is what makes a one-number summary possible, and it is
the reason the "detectable effect" tables below are indexed by discordance rather than by an assumed
baseline rate. The exact computation is cross-checked against the original combinatorics-based
formula over the 12 original cells: `max_abs_difference = 1.53e-14`.

### 7.3 Gate power at the frozen thresholds

Power of the comparison's **own** rule when the true effect equals that comparison's threshold
(`Delta_CA = 0.08`, `Delta_CB = 0.05`; the C−D column uses `Delta = 0.05` as a reference point
only, since the C−D rule has no threshold):

| `q_total` | C vs A (`+8 pp`) | C vs B (`+5 pp`) | C vs D (at +5 pp) |
|---|---|---|---|
| 0.05 | not attainable | 0.459 | 0.772 |
| 0.10 | 0.457 | 0.441 | 0.459 |
| 0.15 | 0.469 | 0.345 | 0.345 |
| 0.20 | 0.475 | 0.278 | 0.278 |
| 0.30 | 0.437 | 0.206 | 0.206 |
| 0.50 | 0.288 | 0.132 | 0.132 |

### 7.4 The `+8 pp` threshold is a conservatism choice, not a high-power choice

Reading table 7.3: a true C−A effect of exactly `+8 pp` clears the gate in **well under half** of
cohorts at realistic discordance (≈ 0.29–0.47). This is a property of the approved design, and it is
reported here rather than hidden. A GO therefore requires the observed effect to **exceed** the
threshold by a margin; a cohort whose true effect only just reaches `+8 pp` will usually classify as
`C_NO_REPAIR_GAIN`. The thresholds are **not** changed — the owner permitted a change only on a
demonstrable mathematical inconsistency, and this is a power property, not an inconsistency.

### 7.5 What the C−D rule can actually see

Smallest true `Delta` whose exact rule reaches 0.80 power:

| `q_total` | C vs A | C vs B | C vs D |
|---|---|---|---|
| 0.05 | not reachable (max power 0.057 at `Delta = 0.05`) | not reachable (max 0.459) | not reachable (max 0.772 at `Delta = 0.05`) |
| 0.10 | not reachable (max 0.744 at `Delta = 0.10`) | 0.075 | 0.075 |
| 0.15 | 0.11 | 0.09 | 0.09 |
| 0.20 | 0.115 | 0.105 | 0.105 |
| 0.30 | 0.125 | 0.125 | 0.125 |
| 0.50 | 0.155 | 0.155 | 0.155 |

At the realistic middle of that range the C−D rule detects a genuine specificity effect of roughly
**+9 to +10 pp**. That is the mechanically meaningful resolution of the rule, and it is the number
the paper should quote when it reports a `DIAGNOSTIC_NONSPECIFIC` label.

At the lowest discordance (`q_total = 0.05`) the rule cannot reach 0.80 even at its maximum feasible
effect — a null from that region is genuinely inconclusive about specificity, and the artifact says
so explicitly rather than printing a misleading threshold.

### 7.6 How often the C−D rule fires under the null

| `q_total` | exact rule (McNemar only) | simulated full gate |
|---|---|---|
| 0.05 | 0.0154 | 0.0175 |
| 0.10 | 0.0245 | 0.0240 |
| 0.15 | 0.0273 | 0.0190 |
| 0.20 | 0.0273 | 0.0215 |
| 0.30 | 0.0263 | 0.0240 |

≈ 2–3 %, at or below the nominal 0.05 significance level — as it must be for a one-sided exact test

### 7.7 Cross-checks against the frozen analysis code

Both are computed with `tinylean_rl.evaluation.v4_stats` — the same functions the analyzer will call,

### 9.2 The multi-turn pathway exists upstream and is disabled in every project run

The audit searched the repository and the vendored `third_party/kimina-prover-rl` submodule
(HEAD `e16b605e8186614c685875c9b57eb19e841b521a`) for an existing Kimina/Qwen multi-turn or
error-fixing renderer. Finding:

* **It exists.** `recipe/kimina_prover_rl/kimina_prover_rl/dataset.py:220 create_one_multiturn_prompt`
  appends `{"role": "assistant", "content": response}` and then `{"role": "user", "content": feedback}`,
  with a feedback-length guard (`multiturn_max_feedback_length` default 3000, `:92`), a turn budget,
  and a `max_prompt_length` check at `:266`. `reward/error_fixing.py:229 create_tool_message`
  formats the Error message / Goals state / Lean 4 code snippet as a **plain string** — no `tool`
  role. `kimina_prover_0.6B.sh:28-30` launches it with `+data.multiturn=True`.
* **Every project run turns it off.** `configs/rl/kimina_0.6b_pilot.yaml:56 multiturn: false`,
  `scripts/run_p3_pilot.sh:138 +data.multiturn=False`, `scripts/run_p3_smoke.sh:139
  +data.multiturn=False`. So the upstream pathway is *not* a validated inference pathway for this
  project's model — it is a training-data construction that no run here has ever used.
* It is also not equivalent to what V4-P001 needs: it carries no diagnostic normalization, no
  donoring, no per-theorem control, and no way to hold B and C byte-identical apart from the
  diagnostic. Reusing it would silently change the experiment.

**Decision, stated plainly.** `v4-prompt-1` is a **new inference-only message convention** of the
same shape as the upstream pathway — an assistant turn carrying the extracted failed proof, then a
user turn carrying the correction request (and, in C/D, the bounded normalized diagnostic). It is
**not** described anywhere in this package as the model's native chat format, and it is not claimed
to be an upstream-validated format. Its justification from the model's own behaviour is recorded in
the artifact: the frozen Kimina/Qwen3 chat template (sha256
`a55ee1b1660128b7098723e0abcd92caa0788061051c62d51cbe87d9cf1974d8`, 4168 chars) renders a
mid-conversation assistant turn plain (`<|im_start|>assistant\n...<|im_end|>\n`) and appends the
generation suffix `<|im_start|>assistant\n`; a probe render confirms both. The template *supports* a
`tool` role, and the V4 renderer never uses it — as does every arm of every run recorded here.

## 11. Verifier infrastructure (owner §16)

Unchanged from the frozen plan (`experiments/manifests/v4/v4_p001_verifier_plan.json`,
`src/tinylean_rl/verifier/policy.py`, policy v2/B0 with the C′ recovery path):

* a dedicated **sequential** verifier; batch mode degrades to isolation when the canary fails, gated
  by the canary proof (`import Mathlib\ntheorem tinylean_v2_canary : (1 : Nat) = 1 := by rfl`);
* recovery ceiling **192 per run** and **3 per theorem**;
* recovery is journaled, and infrastructure failure is never converted into proof failure;
* theorem success semantics are untouched: canonical score == 1 under the same format-gated Lean

## 13. Freeze boundary (owner §12)

After screening reaches exactly 128 primary semantic failures, the runner **stops before any
second-stage generation**. The process that discovers the cohort does not generate a single
second-stage candidate — this is a structural requirement of the runner, not a convention.

At that boundary the runner writes three artifacts, each with its own hash:

| artifact | content |
|---|---|
| `V4-P001_primary_cohort.json` | the 128 primary theorems, their frozen ranks, error categories, screening provenance |
| `V4-P001_diagnostic_derangement.json` | the mapping, its hash, the same-category match rate, token-length differences, fallback count |
| `V4-P001_second_stage_plan.json` | the A/B/C/D prompt hashes and token counts, the paired seeds, the balanced arm schedule |

At the boundary `second_stage_candidates_generated = 0`, and a deterministic validation command
checks cohort membership, error taxonomy, prompt fit, the derangement, the seed set, the arm
schedule, and that the sealed V3-FINAL-HOLDOUT reserve is untouched. The owner does not need to
select or redesign the cohort; the owner does need to authorize the second stage as a separate step.
This amendment authorizes nothing: the whole package ends at
`V4_FORMAL_SCREENING_AUTHORIZED: NO` / `V4_SECOND_STAGE_AUTHORIZED: NO`.

## 14. Analyzer order (owner §13)

`scripts/v4_p001_analyze.py` runs mechanically in the frozen order:

```
provenance -> complete quadruplets -> N guard -> differential censoring guard
  -> C-A -> C-B -> C-D specificity -> classification -> secondary mechanisms
```

Primary statistics are the exact one-sided paired McNemar, the paired theorem bootstrap CI, and the
raw paired effect in percentage points. **No AUPRC**, no predictive metric, no re-selection of the
cohort, no lowering of N.

## 15. Error-transition analysis (owner §15)

Pre-registered on the frozen `v4-taxonomy-1` categories, mapping each candidate's second-attempt
outcome to exactly one label:

```
SUCCESS | SAME_ERROR_CATEGORY | DIFFERENT_ERROR_CATEGORY | FORMAT_FAILURE | SYNTAX_FAILURE | INFRA_MISSING
```

Reported **separately** for B, C and D. The comparisons of interest are same-error persistence
(B vs C), success (B vs C) and different-error transitions (B vs C). These are **descriptive only**
unless already covered by the primary success endpoints; no transition label enters a GO gate, and
no post-hoc transition result may be promoted into one.
